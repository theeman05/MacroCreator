Codebase Context

Macro Studio is a Windows-only Python + PySide6 automation framework. Its distinctive core is a cooperative scheduler: user "tasks" are Python generators driven by a single TaskWorker QThread over a time-ordered heap — a task that yields a float sleeps that long without blocking others (core/execution/task_worker.py). It supports soft vs. hard (interrupt) pause, threaded tasks for blocking work, exclusive solo mode, and a deadlock watchdog. Users author tasks in code or record mouse/keyboard sequences via the GUI. Vision is mss + OpenCV + Tesseract. Persistence is SQLite. Input uses pydirectinput scan codes so games register it.

  • Crown jewel: the scheduler is intricate, mature — and entirely untested (no pytest/unittest anywhere; test/ is manual macros).
  • Real defects found: an infinite-recursion repeat_delay property (task_manager.py:80-86); a fresh mss.mss() context created on every capture/pixel poll (vision.py:36,64,133) despite the "raw hardware speed" pitch.
  • Extension points already in place: a type registry (@register_handler / GlobalTypeHandler) with CaptureMode overlay capture for Point/Region/Color; a recorder producing TimelineStep sequences with Python export; a profile/task/variable DB model.
  • Landscape signal: comparable tools (Playwright, Power Automate Desktop, AutoHotkey, SikuliX) point hard at two openings — flight-recorder-style debugging of a running automation, and resilience to screen/DPI/layout change (the #1 image-automation complaint).

1.

Step-boundary "flight recorder" & trace viewer

Confidence 85%Complexity HighDX · ObservabilityDifferentiator

The scheduler already stops every task at a clean, discrete boundary each time it yields. Hook that boundary to record a lightweight frame — timestamp, which task, the line it yielded on, active variable values, and (optionally) a downscaled screenshot — into a ring buffer. Add a "trace viewer" panel that lets you scrub a completed or failed run step-by-step: what the screen looked like, what the automation believed, and where it diverged.

Basis
direct task_worker.py:250-257 — wait_duration = next(controller), reschedule at current_time + wait_duration: a discrete per-step boundary confirmed in the run loop. external Playwright Trace Viewer (per-action DOM snapshot + before/after screenshots + time-travel scrubbing) is the most-praised debugging UX in the automation-authoring space.
Rationale
Debuggability is the biggest gap in scripting-style automation tools (AutoHotkey's weak debugging is a recurring complaint). Macro Studio has a structural advantage nobody else here has for free: cooperative yields are the trace points. A flight recorder turns "it stopped working, no idea why" into a scrubbable replay — the single most differentiating direction in the set.
Downsides
Screenshot capture per step has cost/storage implications (mitigate: downscale, ring-buffer, make screenshots opt-in per task). Capturing locals cleanly across generator frames needs care. UI surface is non-trivial.
2.

Deterministic scheduler test harness

Confidence 88%Complexity MediumReliability · Leverage

Build a virtual-clock + fake-input test rig for the engine so the heap ordering, soft/hard pause, _generation invalidation, solo-lock, and watchdog logic can be unit-tested without real time or real input. Tasks become deterministic: advance the clock, assert wake order and state transitions.

Basis
direct Repo-wide search finds no pytest/unittest/def test_; test/my_tester.py is a manual macro. The most intricate, correctness-critical code in the project (the pause/generation state machine per CLAUDE.md) has zero automated coverage. reasoned A virtual clock is the standard way to make time-ordered schedulers testable; the engine's own yield-a-duration contract already abstracts wall-clock time, so injecting a fake clock is a small seam.
Rationale
This is the highest-leverage reliability investment: it de-risks every other idea here (a flight recorder, self-healing targeting, and hardening fixes all touch the engine), and turns the "crown jewel" from a change-at-your-peril black box into something you can refactor confidently.
Downsides
Requires threading the clock/input as injectable seams — some refactoring of currently-hardcoded time/input calls. No user-visible payoff on its own, so it competes with feature work for attention.
3.

Resilient targeting: multi-anchor "Target" type + self-healing

Confidence 82%Complexity HighReliability · Feature

Introduce a first-class Target type (registered on the existing type system) that stores several ways to find the same on-screen thing — a template image, an OCR text label, a bounding region, an anchor color — and resolves at runtime by trying them in order with confidence thresholds. On a miss, fall back to the next anchor (or multi-scale matching) and re-anchor the coordinate rather than failing the whole task.

Basis
direct The type registry (type_handler.py:201, @register_handler) and CaptureMode (POINT/REGION/COLOR overlay capture, types_and_enums.py:11-14) already exist — a composite Target is a natural addition on this seam, not a new subsystem. external Power Automate Desktop ships runtime "self-healing" (re-finds a changed element); SikuliX's well-documented failure mode is that single-image matching breaks on resolution/scale/layout change — the exact fragility Macro Studio's OpenCV matching inherits today.
Rationale
Fragility to screen/DPI/layout change is the #1 complaint in image-based automation. Storing redundant anchors and degrading gracefully is what separates a toy record-replay from something that survives a game patch or a window move — and it slots directly onto infrastructure the project already has.
Downsides
Capturing multiple anchors adds authoring friction (mitigate via the overlay capture flow). Ordering/threshold heuristics need tuning. OCR anchors depend on Tesseract being present (see idea 7).
4.

Recorder → editable, assertion-based timeline

Confidence 80%Complexity MediumAuthoring · UX

Let a recorded sequence be refined, not just replayed: edit steps, and insert wait-until vision assertions ("wait until this image/text appears") in place of the brittle fixed sleeps that recordings bake in. Pairs naturally with the Target type (idea 3) as the thing an assertion waits on.

Basis
direct The recorder already produces TimelineStep sequences (timeline_handler.py:33) and exports to standalone Python — the editable-model substrate exists. external Pulover's Macro Creator's whole value over TinyTask is that recorded rows are editable; Playwright's codegen inserts auto-assertions rather than raw waits. Both are proven patterns.
Rationale
Fixed sleeps are the most common reason recorded macros are flaky and slow — too short and they race, too long and they waste time. Assertion-based waits make recordings both faster and more robust, and turn the recorder from a novelty into a real authoring path that graduates into editable code.
Downsides
A step-editing UI is real surface area. Assertion capture needs the overlay flow. Overlaps idea 3 — best sequenced after (or with) it.
5.

Headless runner + triggers

Confidence 68%Complexity MediumFeature · Reach

Run tasks without the GUI, started by triggers rather than a human pressing F6: a schedule (cron-like), a global hotkey, or a screen-state condition ("when this image/color/text appears, run task X"). Turns Macro Studio from an interactive tool into something that can run unattended.

Basis
reasoned Constraint flip — "what if there were no GUI?" The engine (MacroStudio/TaskWorker) is already decoupled from the UI via Qt signals per CLAUDE.md, so a headless driver is mostly a new entry point plus a trigger loop, not an engine rewrite. Screen-state triggers reuse the vision stack. external Pulover's Macro Creator's built-in scheduler (run-on-startup) is a headline feature; event-driven "run when X appears" is standard in RPA.
Rationale
Unattended operation is a category expansion — ergonomic auto-toggles, watchers, and scheduled chores are common real-world drivers that the current human-in-the-loop model can't serve. It also unlocks the value of idea 6 (a shared task is far more useful if it can run on a trigger).
Downsides
Screen-state polling has a cost/latency budget; needs the cached-capture fix (idea 7) to be cheap. Unattended runs raise the stakes on reliability (leans on ideas 2 and 3). Trigger config is new UI.
6.

Task/profile share & import format

Confidence 66%Complexity MediumDistribution · Compounding

A portable export/import format bundling a task (or profile) with its variables and captured targets, so users can share automations — and optionally a one-click "compile to standalone .exe" for install-free distribution.

Basis
direct The DB already models profiles, tasks, per-relationship repeat/is_enabled, and per-profile variables (database_manager.py) — the export unit is well-defined. A PyInstaller spec already exists for the .exe path. external AutoHotkey's culture — compile-to-exe plus a forum/script-sharing ecosystem — is a large part of why it spread.
Rationale
Shareability compounds: every shared, runnable task lowers the bar for the next user and seeds a library/community. It's how a single-developer tool grows reach without proportional developer effort.
Downsides
Shared arbitrary-Python tasks raise a trust/safety question (a sandbox is a downstream concern, deliberately deferred here). Bundling captured images/targets portably (across resolutions) is fiddly. Adoption depends on there being users to share with.
7.

Foundation-hardening bundle

Confidence 90%Complexity LowCorrectness · Quick wins

A tight cluster of concrete, verified fixes worth doing as one pass: (a) fix the infinitely-recursive repeat_delay property; (b) cache/thread-local the mss capture instance instead of creating one per poll; (c) make the watchdog release held keys and attempt a cooperative cancel before the nuclear QThread.terminate(); (d) replace the hardcoded Tesseract path with PATH/registry auto-detection.

Basis
direct Verified against the repo: repeat_delay getter returns self.repeat_delay and setter assigns self.repeat_delay with no backing field (task_manager.py:80-86) — any access via engine.py:60/65 is a genuine RecursionError. Every capture path opens with mss.mss() per call (vision.py:36,64,133), contradicting the "raw hardware speed" pixel-scan pitch. The watchdog does worker.terminate() + rebuild (task_manager.py:200-203), which can strand held keys. Tesseract path is hardcoded at vision.py:8.
Rationale
These are small, high-confidence, individually-below-the-ambition-floor fixes — but as a bundle they're a real "harden the foundation" decision that removes a live crash path and closes the gap between the README's performance claims and the code. Best done under the safety net of idea 2.
Downsides
Thread-local mss must respect that mss instances aren't shareable across threads. A graceful watchdog cancel needs a bounded timeout before falling back to terminate, so it doesn't reintroduce the deadlock the watchdog exists to break.
